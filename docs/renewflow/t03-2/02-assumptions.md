# T03.2 假設與決策

以下是**工程假設**，不是公司的正式制度。

## 使用者已確認的工程假設

| 編號 | 內容 |
|---|---|
| A-30 | 半徑允許 10～5000 公尺，可由管理員調整 |
| A-31 | 可接受的 accuracy 上限固定 50 公尺，集中定義於後端 `GeofenceRules.MAX_ACCURACY_METERS`，經 API 告知前端 |
| A-32 | 先檢查定位品質，再判斷距離；距離 ≤ 半徑才可打卡；不把 accuracy 加進半徑 |
| A-33 | 以定位中心點判斷，不宣稱整個誤差圓都在公司內 |
| A-34 | 定位時間接收窗口：伺服器現在往前 60 秒、往後 10 秒；用戶端時鐘偏差可能導致誤判 |
| A-35 | 定位時間是用戶端資訊，不證明位置真實、不防重播；出勤時間完全來自伺服器 Clock |

## 本階段補充的假設與決策

| 編號 | 內容 | 理由 | 未採用 |
|---|---|---|---|
| A-36 | 設定是單一列（`id = 1`，CHECK 限制），由 V4 建立預設值 | 第一版只有一個公司地點；不必處理「沒有設定列」的分支 | 每次修改新增一列：讀取要找最新一列，並行較難推理 |
| A-37 | 距離用 Haversine，地球平均半徑 6,371,008.8 公尺（IUGG） | 公尺級範圍內誤差遠小於瀏覽器定位誤差；計算簡單可測 | Vincenty（橢球）：較精確但複雜；本規模不需要 |
| A-38 | 定位檢查先於出勤規則（例如已上班又按上班，受限制時先回定位錯誤） | 所有定位拒絕都在寫入前，不影響資料 | 先查出勤狀態：需在鎖住設定前多查一次 |
| A-39 | 每次成功打卡（不論是否要求定位）都寫一筆打卡事件；不受限制時不存座標 | 證據完整、可追溯「當時是否要求定位、用哪一版設定」 | 只在受限制時寫：無法回答「當時為何沒要求」 |
| A-40 | 前端按下按鈕時先取最新定位要求，再決定是否定位；若後端仍回 `LOCATION_REQUIRED`，不自動重送 | 減少競態；避免未經使用者再次確認就送出 | 自動補定位重送：使用者不知道發生了什麼 |
| A-41 | 員工端只取得「是否需要、半徑、精度上限」，不取得公司中心座標 | 最小揭露 | 回傳中心：前端用不到 |
| A-42 | 測試資料庫是拋棄式：後端測試每次重置設定；E2E 隔離後端啟動時把設定重置為預設值（不寫歷程，只限測試庫） | 前一次測試殘留的「已啟用」不會影響其他 E2E | 依賴每支腳本自行還原：腳本中斷時會殘留 |

## 決策

| 編號 | 決策 | 理由 | 未採用 |
|---|---|---|---|
| D-31 | 打卡交易以 `SELECT … FOR SHARE` 鎖設定列取得快照；設定更新以 `SELECT … FOR UPDATE`＋版本條件 UPDATE | 打卡彼此不互鎖；設定更新會等進行中的打卡結束，之後的打卡會讀到新版本，先後明確、可測 | 不鎖、只讀：可能在讀取後被改，證據與判斷不一致；SERIALIZABLE：重試成本高 |
| D-32 | 打卡事件獨立成 `attendance_clock_event`，只新增（觸發器擋 UPDATE／DELETE） | 出勤時間可更正，原始證據不可改 | 把座標放在 `attendance` 欄位：更正或重打會覆蓋 |
| D-33 | 不對「出勤 ID＋操作」做唯一限制 | 撤銷下班後再下班會合法產生第二筆下班事件 | 唯一限制：擋掉合法重打 |
| D-34 | 範圍外用 403 `OUTSIDE_GEOFENCE`，定位品質不足用 422 | 依使用者指定；與 409 的出勤衝突區分 | 全部 400：前端無法區分可重試的情況 |
| D-35 | 設定歷程獨立成 `geofence_setting_history`，只新增 | 與出勤歷程的欄位完全不同 | 合併進 `attendance_history`：欄位語意混雜 |
