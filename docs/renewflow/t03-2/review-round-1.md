## 1. 問題

### R1：等待定位設定期間切頁，舊操作仍可能定位或打卡
`useTodayAttendance.perform` 的取消防護只放在「定位結果回來之後」。員工按下打卡、`fetchLocationPolicy()` 尚未回來時切頁（卡片卸載）：
- 設定回「不需定位」→ 舊操作仍呼叫 `clockIn()`（送出 POST）。
- 設定回「需要定位」→ 舊操作仍先呼叫瀏覽器定位，之後才發現已卸載。

### R2：今日狀態的舊回應覆蓋新回應
`reload()` 只檢查 mounted。兩次查詢 A（舊）、B（新）：B 先回 WORKING，A 才回 NOT_STARTED → 畫面被改回「尚未上班」；等待中的定位回來後 `stillAllowed()` 依舊狀態允許送出上班 POST（後端會以 409 拒絕，但前端已丟掉自己取得的新狀態）。

## 2. 修正（`frontend/src/attendance/useTodayAttendance.ts`）

| 項目 | 做法 |
|---|---|
| 掛載有效期間 | 每次掛載建立新的 `Lifetime { alive }` 物件，卸載時設為 false 且永不復活；StrictMode 的「卸載再掛載」會換新物件，舊流程不會被誤認為有效 |
| 打卡操作識別 | `Operation { id, action, lifetime }`；`activeOperation` ref 指向目前操作。有效＝所屬掛載仍有效且仍是目前操作 |
| 檢查點 | 設定回來後、呼叫定位前、定位回來後、送出 POST 前、打卡後的確認查詢之後；需要定位與不需要定位走同一個「送出前」檢查（含 `stillAllowed`） |
| 過期操作 | 不定位、不送出、不更新畫面、不呼叫 `onChanged`、不清掉較新操作的 busy |
| 今日狀態查詢 | 唯一入口 `load()`：每次發出取得新序號，只有「最後發出的那一次」的成功或失敗會被採用；過期的 401 不觸發登入狀態刷新 |
| 最新狀態 | 採用回應時同步更新 React state 與 `latestState` ref（不再等 effect） |
| 入口統一 | 首次載入、手動刷新、回到前景、跨日、申請結果、打卡後、重試都呼叫 `load()` |

取消的界線：POST **送出前**卸載 → 一定不送；POST **送出後**卸載 → 前端不再更新畫面，但不宣稱能撤回伺服器的寫入；重新進入畫面時查詢真實狀態，不自動重送。

## 3. 驗收情境（`frontend/e2e/geofence-races.mjs`，`npm run e2e:races`）

以請求攔截（扣住、放行、偽造、中斷）與手動定位安排事件先後；只有「不應發生」的斷言在事件確定送達後等待一小段固定時間。

| 編號 | 情境 | 預期 |
|---|---|---|
| R1-1 | 設定未回來就切頁，之後回「不需定位」 | 0 次定位、0 次 POST；新頁面卡片不受影響 |
| R1-2 | 同上，之後回「需要定位」 | 0 次定位、0 次 POST |
| R1-3 | 定位已開始後切頁，晚到的成功／失敗 | 不送出；新頁面不顯示舊錯誤 |
| R1-4 | 新頁面的新操作正在定位時，舊操作的設定才回來 | 舊操作不送出；新操作仍在進行並正常完成（恰 1 次 POST） |
| R2-1 | 新查詢先回 WORKING、舊查詢後回 NOT_STARTED；之後定位成功 | 維持工作中；取消原上班操作，上班／下班 POST 皆 0 |
| R2-2 | 舊查詢晚到的 500 | 不覆蓋新的成功 |
| R2-3 | 新查詢失敗、舊查詢晚到成功 | 仍顯示錯誤；重試可恢復 |
| R2-4 | 過期的 401／最新的 401 | 前者不刷新登入狀態；後者依既有流程重新確認 |
| R2-5 | 最新查詢網路中斷 | 顯示錯誤與重試，不登出 |
| R2-6 | 首次載入（StrictMode 下 2 次）比重新查詢晚回且失敗 | 不覆蓋 |
| R2-7 | 打卡後的確認查詢被較新的刷新取代 | 以最新查詢為準；POST 恰 1 次，不重送 |

**舊行為被抓到**：同一支測試在修正前的程式（`2d6f333`）執行 → 22 項中 11 項失敗（R1-1、R1-2、R1-4×2、R2-1×2、R2-2、R2-3、R2-4、R2-6、R2-7）。R1-3 在修正前已通過（舊程式在定位回來後有檢查），保留作為回歸防護。修正後 22/22。
