# T03.2 需求與領域分析：公司範圍定位打卡與管理員設定

原始指南第 2 節把「GPS／人臉打卡」列為「暫不加入」，那是**原始範圍**。使用者於 2026-10-02 明確授權 T03.2 加入「公司範圍定位打卡」。人臉、設備打卡與其他項目仍不在範圍內。

## 1. 角色與使用案例

| 角色 | 使用案例 |
|---|---|
| ADMIN（`admin`、`developer` 權限相同） | 設定是否啟用、公司中心、允許半徑、適用操作；每次變更填原因並確認修改前後差異；查看設定歷程；自己打卡也遵守設定 |
| EMPLOYEE／MANAGER | 按下需要定位的打卡按鈕時提供瀏覽器位置；範圍外被拒絕時看到距離與允許半徑；在範圍外仍可提出撤銷下班、整組作廢、更正／補登申請 |
| 系統 | 以伺服器 Clock 與後端計算決定是否接受打卡；保存成功打卡的原始證據 |

`developer` 沒有任何隱藏的定位繞過權限。

## 2. 領域名詞

| 名詞 | 說明 |
|---|---|
| 定位設定（geofence setting） | 單一公司地點：啟用旗標、中心緯經度、半徑（公尺）、適用操作、版本 |
| 適用操作（scope） | `CLOCK_IN`、`CLOCK_OUT`、`BOTH` |
| 定位資料 | 瀏覽器提供的緯度、經度、accuracy（95% 信心半徑，公尺）、取得時間 |
| 距離 | 後端以 Haversine 計算的定位中心點與公司中心的大圓距離 |
| 打卡事件（clock event） | 一次**成功**打卡的原始證據；只新增，不因更正、作廢、補登而改寫 |
| 設定歷程 | 每次設定變更的前後值、原因、修改人、時間；只新增 |

## 3. 規則

1. 預設：關閉、公司中心未設定、半徑 100、適用上下班。管理員設定有效中心後才能啟用。不填入虛構公司位置。
2. 啟用且本次操作在適用範圍內，才需要定位；否則沿用原本流程，不要求定位權限。
3. 受限制時：先通過定位品質（欄位齊全、有限數值、accuracy ≤ 50、時間窗口），再判斷距離；距離 ≤ 半徑才可打卡。
4. 不把 accuracy 加進半徑；判斷的是定位**中心點**，不宣稱整個誤差範圍都在公司內。
5. 設定變更需原因、版本比對（過期提交 409）、留下只新增的歷程。
6. 打卡與設定變更有明確先後：每次打卡只使用單一版本的完整設定。
7. 打卡事件保存實際採用的設定版本與內容；受限制時才保存員工座標。
8. 申請（撤銷下班、整組作廢、更正／補登）不受定位限制；核准不製造定位證據；核准後的下一次實際打卡遵守當下設定。

## 4. 不變條件

1. 定位拒絕不改動出勤、版本，也不建立打卡事件。
2. 出勤寫入與打卡事件寫入同成同敗。
3. 設定更新與設定歷程同成同敗。
4. 打卡事件與設定歷程不可透過一般 API 或 SQL UPDATE／DELETE 修改。
5. 設定讀取失敗時拒絕打卡（500），不當作關閉放行。
6. T03／T03.1 的不變條件全部保留（每人每日一筆有效紀錄、ID＋版本、申請只處理一次、歷程同交易）。

## 5. 明確不做

多據點、地圖選點、地址搜尋、持續追蹤（`watchPosition`）、Wi-Fi／IP 限制、人臉、外勤核准、即時地圖、定位歷程頁、HTTPS 憑證或隧道、部署。

## 6. 未知與限制

- 瀏覽器定位可能來自 GPS、Wi-Fi 或 IP，可被模擬或偽造；本功能**不能**完全防止代打卡或作弊。
- `capturedAt` 是用戶端資訊，不能證明位置真實，也不能防止重播。
- 手機透過區網 HTTP 位址開網站不是安全來源，瀏覽器可能拒絕定位；本階段沒有 HTTPS 實機驗證。
