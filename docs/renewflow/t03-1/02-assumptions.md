# T03.1 學習假設與決策

| 編號 | 假設 | 影響 |
|---|---|---|
| A-15 | ADMIN 是本階段最高管理權限；不新增更高或可繞過檢查的角色 | 權限模型 |
| A-16 | 重新打卡申請只適用「今日」；已跨過台北日期不可核准，改用歷史時間更正 | RESET_TODAY |
| A-17 | 更正／補登仍是「同一台北日的白班」：時間必須落在該業務日、不得為未來、下班不早於上班；可申請撤銷誤按的下班（恢復工作中／未完成） | CORRECT_TIME |
| A-18 | 同一員工同一日期最多一筆待審申請（不分類型） | 唯一索引 |
| A-19 | 管理員不能審核自己的申請，也不能直接更正自己的出勤（職責分離）；開發時用 developer 與 admin 互相／為 employee 處理 | 授權 |
| A-20 | 直接作廢只限「今日」的紀錄（目的：開放重新打卡）；過去的日期用時間更正 | 管理員操作 |
| A-21 | 本機開發帳號 `developer`（ADMIN）使用獨立密碼環境變數，沒有預設密碼；沒設定就不建立並明確提示 | 開發帳號 |
| A-22 | 員工看得到自己歷程中的操作者顯示名稱（透明度）；不顯示密碼或身分識別以外的資訊 | 歷程 |

## 決策紀錄

| 編號 | 決策 | 原因 | 替代方案與成本 |
|---|---|---|---|
| D-19 | 重新打卡＝作廢舊紀錄＋再新增有效紀錄；唯一限制改為**部分唯一索引**（`WHERE voided_at IS NULL`） | 保留原始資料；仍由資料庫保證只有一筆有效紀錄；`INSERT ... ON CONFLICT (employee_id, work_date) WHERE voided_at IS NULL` 的衝突目標必須與索引條件一致 | 硬刪舊紀錄：失去證據；無條件唯一限制：無法保留多筆作廢歷史 |
| D-20 | 出勤紀錄加 `version`，所有寫入（含 T03 的原生上下班 SQL）都 `version = version + 1`；核准以「id＋version＋未作廢」條件更新，0 筆＝過時 | 簡單、可在單一 SQL 內檢查，不需要長時間持鎖 | JPA `@Version`：本專案寫入走原生 SQL，需同步維護；悲觀鎖：較重 |
| D-21 | 申請狀態轉移以條件更新（`WHERE status = 'PENDING'`）完成，且先做（鎖住申請列）再改出勤 | 同一申請只能被處理一次；並行核准／退回／撤回只有一個成功；失敗時整個交易回滾 | 先讀後改：有競態 |
| D-22 | 歷程表以資料庫觸發器禁止 UPDATE／DELETE | 不只靠「沒有 API」，連直接下 SQL 也擋（測試庫清理改用 TRUNCATE） | 只靠應用程式：較弱 |
| D-23 | 歷程以 JPA 新增（失敗丟例外→交易回滾），由 `AttendanceAuditLog` 單一元件寫入 | 測試可替身注入失敗，驗證回滾 | 在各處直接 save：難以集中驗證 |
| D-24 | 管理 API 一律在 `/api/admin/**`，Security 規則 `hasRole('ADMIN')`＋Service 內再檢查角色（縱深防禦） | 後端驗證；URL 規則易於審查 | 只靠 `@PreAuthorize`：需另外啟用方法安全 |
| D-25 | E2E 保護提前：以 `FlywayMigrationStrategy`（在 migrate 之前）檢查 Flyway 實際使用的 datasource；種子資料也在寫入前檢查 | 之前在 `ApplicationRunner` 才檢查，migration 早已執行 | 只在 runner 檢查：錯誤設定時已套用 migration |
| D-26 | 前端以 focus／visibilitychange／每分鐘檢查台北日期／待審時每 30 秒輪詢來重新取得狀態；不用 WebSocket | 簡單、足夠、不新增套件 | WebSocket／SSE：本輪過度設計 |
