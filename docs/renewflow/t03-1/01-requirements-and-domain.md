# T03.1 需求與領域分析：出勤更正、重新打卡申請與管理權限

產品：TeamPortal（企業員工入口平台）。方法：RenewFlow Engineering Method v2。
狀態：已實作並由作者驗證（證據見 `docs/learning/T03-1-attendance-corrections.md`）；**尚未經對話助理審查**。

## 1. 為什麼需要它

T03 的規則是「每人每日一組、不能修改或刪除」。實際使用時（例如今天測試功能誤按上下班）員工被卡住：當天無法再打卡。T03.1 提供**受控、有歷程**的出路——員工提出申請，管理員審核；不是讓員工自己改資料，也不是直接刪除。

## 2. 事項分級

| 類別 | 內容 |
|---|---|
| 已確定（使用者授權） | 兩種員工申請（重新打卡、更正／補登）；ADMIN 為本階段最高管理權限；申請狀態 PENDING／APPROVED／REJECTED／CANCELLED；管理員可審核並可直接更正；全程歷程；重新打卡＝作廢舊紀錄再新增；部分唯一限制；版本衝突檢查；E2E 資料庫保護提前到 migration 之前 |
| 學習假設（不代表公司制度） | 見 `02-assumptions.md`（A-15～A-22） |
| 不做 | 員工管理 CRUD、全員統計報表、工時／請假、跨日班／輪班、未來時間、WebSocket、新 UI／路由套件、修改／刪除歷程的任何 API |

## 3. 角色

| 角色 | 本階段能做的事 |
|---|---|
| EMPLOYEE | 對**自己**提出申請、撤回自己的待審申請、查看自己的申請與歷程 |
| MANAGER | 同 EMPLOYEE。**不自動取得**管理權限 |
| ADMIN | 同 EMPLOYEE，另可：審核（核准／退回）他人的申請、查詢任一員工的出勤、直接更正他人的出勤或作廢其今日紀錄、查看歷程 |

- 沒有新增可繞過安全檢查的角色。`admin`（既有）與 `developer`（新增，僅 dev 初始化）都是 ADMIN。
- **職責分離**：ADMIN 不可審核（核准或退回）自己提交的申請，也不可直接更正自己的出勤。
- 管理權限由後端驗證（`/api/admin/**` 需要 `ROLE_ADMIN`，且 `ActiveAccountFilter` 會先確認角色仍是最新）；畫面只是隱藏入口。

## 4. 使用案例

| 編號 | 案例 | 正常結果 | 異常結果 |
|---|---|---|---|
| UC-21 | 員工申請重新打卡（RESET_TODAY） | 建立 PENDING 申請；出勤資料不變、按鈕不開放 | 今日沒有有效紀錄 409 `NO_RECORD_TO_RESET`；已有待審 409 `DUPLICATE_PENDING_REQUEST`；原因空白 400 |
| UC-22 | 員工申請更正／補登（CORRECT_TIME） | 建立 PENDING 申請（含原值與希望值） | 時間不合理 400 `INVALID_REQUEST`（未來、下班早於上班、非該日、無變更）；重複待審 409 |
| UC-23 | 員工撤回待審申請 | 狀態 CANCELLED | 非待審 409 `REQUEST_NOT_PENDING`；別人的申請 404 |
| UC-24 | 管理員核准 RESET_TODAY | 原紀錄**作廢並保留原時間**，今日回到尚未上班，可重新打卡一組 | 已跨日 409 `RESET_DATE_PASSED`；資料已變動 409 `REQUEST_STALE`；自己的申請 403 |
| UC-25 | 管理員核准 CORRECT_TIME | 更新（或建立）該日有效紀錄的時間 | 資料已變動 409 `REQUEST_STALE`；非待審 409 `REQUEST_NOT_PENDING` |
| UC-26 | 管理員退回 | 狀態 REJECTED；**原因必填**；出勤不變 | 原因空白 400 |
| UC-27 | 管理員直接更正／作廢今日 | 必填原因、需版本相符；寫入歷程 | 版本不符 409 `RECORD_CHANGED`；對象是自己 403；非今日作廢 409 `VOID_DATE_PASSED` |
| UC-28 | 查看歷程 | 員工看自己的；管理員看指定員工與區間 | — |
| UC-29 | 一般員工／主管呼叫管理 API | 403 | 未登入 401 |

## 5. 領域名詞與不變條件

- **有效紀錄**：未被作廢的出勤紀錄。**每人每個業務日期最多一筆有效紀錄**（可有多筆作廢歷史）。
- **作廢（void）**：把舊紀錄標記為作廢，**保留原上下班時間**，不硬刪。作廢者與時間被記錄。
- **申請（attendance request）**：員工提出的「希望值」；核准前不改正式出勤。
- **歷程（attendance history）**：僅新增的操作紀錄，包含申請人、日期、操作類型、原因、目標紀錄與版本、原值、申請值、實際修改前後值、操作者、審核結果、伺服器時間。
- **版本（version）**：每筆出勤紀錄每次被修改就加一。申請會記住建立當下的版本；核准時必須相同，否則是**過時申請**。

不變條件：
1. 每人每日最多一筆有效紀錄（資料庫部分唯一索引保證）。
2. 每人每日最多一筆待審申請（資料庫部分唯一索引保證）。
3. 申請只能從 PENDING 轉為 APPROVED／REJECTED／CANCELLED，且一次（條件更新保證）。
4. 核准時的出勤修改、申請狀態更新、歷程寫入**在同一交易**；任一失敗全部回滾。
5. 歷程不可修改、不可刪除（資料庫觸發器擋 UPDATE／DELETE；沒有對應 API）。
6. 核准不得覆蓋較新的出勤資料（版本比對）。
7. 退回必有原因；員工與管理員的身份、操作時間都由後端產生。

## 第 1 輪複審後的調整（詳見 `review-round-1.md`）

員工端今日的申請分成三種操作，對資料的影響不同：

| 操作 | 何時出現 | 核准後 |
|---|---|---|
| 申請撤銷下班打卡 | 今日有效紀錄**已有下班** | 同一筆紀錄：上班時間不變、下班清空、版本 +1、恢復工作中，可再下班 |
| 申請整組作廢並重新打卡 | 今日有有效紀錄（只有上班也可以） | 整筆作廢（原時間保留在歷程），今日回到尚未上班 |
| 申請更正／補登時間 | 任何今日或過去日期 | 依申請值更正或建立 |

不提供「只取消上班、保留下班」。

新增不變條件：
8. 直接更正以「紀錄 ID＋版本」指定目標，被作廢或換成另一筆（即使版本號碼相同）都不會被改到。
9. 員工提出申請時，表單看到的紀錄（ID＋版本，或「沒有紀錄」）必須仍是目前的有效紀錄。
