# T05：安全設計

## 1. 權限與資料範圍

| 操作 | EMPLOYEE | MANAGER | ADMIN |
|---|---|---|---|
| 送出、查看、撤回**本人**申請 | ✔ | ✔ | ✔ |
| 查看他人申請 | 404 | 只有**指派給自己**的 | 管理 API 可查全部 |
| 核准、退回 | — | 只限指派給自己的 | 只限指派給自己的（不能憑 ADMIN 身分繞過） |
| 改派 | 403 | 403 | ✔（不能改派自己的申請） |
| 指定請假審核人 | 403 | 403 | ✔ |

- 角色（能做哪類操作）與資料範圍（能操作誰）分開檢查。SQL 以 `employee_id = 我` 或 `approver_id = 我` 限定。
- MANAGER 不因此取得任何出勤、工時或員工管理權限。
- **禁止自審**：審核人不是申請人（送出時、改派時、指定設定時都檢查；資料庫 CHECK 最後一道）。ADMIN 不能改派自己的申請。developer 只是一般 ADMIN，沒有繞過。
- 不存在、他人的、非指派的、已改派走的申請：一律 404 `LEAVE_NOT_FOUND`，不洩漏內容或是否存在。

## 2. 身分與時間由後端決定

- 申請人取自 Session，不接受本文的 `employeeId`。
- 審核人由後端決定；狀態、決定者、時間（`Clock`）、分鐘數都由後端計算。
- `requestId` 只在「同員工」內比對：查詢條件一定帶 `employee_id`，無法用來探測他人的申請。

## 3. 等待鎖期間的權限變化（D-71）

請求通過 `ActiveAccountFilter` 之後才取組織鎖。等待鎖的期間，操作者可能被停用或改角色。所以**取得鎖後**再讀一次帳號狀態：
- 已停用、已刪除或角色不同 → 401 `UNAUTHENTICATED`，交易內沒有任何寫入。前端走既有的「登入失效 → 回登入頁」流程。
- 下一個請求由 Filter 作廢 Session。
- 讀取帳號狀態時資料庫故障 → 500（不冒充未登入）。

## 4. 輸入與輸出

- 原因最多 500 字，不收集醫療資訊；畫面提示不要填寫診斷內容。
- 回應不含密碼、雜湊、SQL 或內部例外；驗證錯誤只回欄位名稱。
- 沿用 Session＋HttpOnly Cookie、CSRF、錯誤遮蔽。
