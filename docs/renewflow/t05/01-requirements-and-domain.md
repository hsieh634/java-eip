# T05：需求與領域分析——請假申請與主管審核

> T05 正式功能（T05 前置的組織資料已完成並通過複審）。本文件的假別、時段與審核規則是 **STMAX 示範規則／本批工程假設**，不是正式人事制度，也不代表符合勞動法規。

## 1. 目標

**員工送出請假 → 指定審核人核准或退回 → 員工查看結果／撤回待審申請 → 保留歷程。**

## 2. 與原始指南的差異（取捨）

| 原始描述（學習指南第 2、6 節） | 本批 | 理由 |
|---|---|---|
| 草稿、送出、單一指定主管核准／退回 | 沒有草稿：送出即為待審；可撤回待審 | 本批授權範圍明列「送出、撤回、核准、退回、改派」，沒有草稿；撤回＋重新送出可涵蓋修改需求 |
| 審核人：指定主管 | 直屬主管為預設；ADMIN 可設定「指定請假審核人」優先 | 解決「沒有主管的人（Max）」由誰審核，又不能改組織主管關係 |

## 3. 角色與使用案例

| 角色 | 使用案例 |
|---|---|
| 任何已登入員工（含 MANAGER、ADMIN） | 送出本人請假；查看本人清單、詳情、狀態、退回原因、歷程；撤回本人**待審**申請；查看「預計審核人」提示 |
| 審核人（被指派的 MANAGER／ADMIN） | 只查看**指派給自己**的申請；核准；退回（原因必填） |
| ADMIN | 查詢所有申請與歷程；改派待審申請（原因必填）；管理「指定請假審核人」（版本、原因、歷程）。**不能**憑 ADMIN 身分核准或退回未指派給自己的申請 |

## 4. 領域名詞

| 名詞 | 說明 |
|---|---|
| 請假申請（LeaveRequest） | 一個台北業務日期內的一段時間：`[開始, 結束)`；有假別、原因、狀態、審核人、版本 |
| 假別（LeaveType） | `PERSONAL` 事假、`SICK` 病假、`ANNUAL` 特休（示範規則，沒有額度） |
| 申請時段長度 | 結束 − 開始的分鐘數，由後端計算；**未扣除休息時間，不是計薪工時，也沒有扣抵任何額度** |
| 審核人（approver） | 送出時決定並保存的員工 ID（快照）；之後只有 ADMIN 改派會改變它 |
| 指定請假審核人（approver setting） | ADMIN 對某位員工設定的請假審核人，優先於直屬主管；不影響組織的主管關係 |
| 改派（reassign） | ADMIN 把待審申請換給另一位有效的 MANAGER／ADMIN |
| 請假歷程 | 只新增：送出、核准、退回、撤回、改派、指定設定修改 |

## 5. 規則

**時段**：
- 一筆申請只在一個業務日期內，不跨午夜。跨日請分開送出。
- 開始與結束都在半小時刻度上，且結束嚴格晚於開始。
- 日期可以是過去、今天或未來，但限制在今天前後 365 天內（A-81）。

**原因**：必填，去除前後空白後 1～500 字。不收集醫療證明或診斷。

**狀態轉移**：
- PENDING → APPROVED（目前審核人）
- PENDING → REJECTED（目前審核人，原因必填）
- PENDING → WITHDRAWN（申請人）
- PENDING 改派：狀態不變，版本 +1
- 其他轉移一律拒絕。APPROVED、REJECTED、WITHDRAWN 都是終態：已核准的申請本批**不能**修改、撤回或取消，ADMIN 也沒有隱藏的修改入口。

**重疊**：
- 同一員工的 PENDING、APPROVED 申請時段不可重疊（半開區間，12:00 結束與 12:00 開始可以並存）。
- REJECTED、WITHDRAWN 不占時段。

**審核人決定**（送出時，依序）：
1. 有指定請假審核人 → 使用它。若它已無效（停用、不是 MANAGER／ADMIN），拒絕送出並提示管理員更新，**不會**自動退回採用直屬主管（A-83）。
2. 否則採直屬主管。
3. 兩者都沒有 → 拒絕送出，提示需要管理員設定。

審核人一定是啟用中的 MANAGER 或 ADMIN，且不是申請人本人。

**快照**：送出後審核人不隨主管或指定設定變更而改變。審核人被停用或降成 EMPLOYEE 後不能審核，由 ADMIN 改派。

**改派**：
- 只限 PENDING，原因必填，需要 ID＋版本。
- 新審核人必須有效，不能是申請人，也不能與原審核人相同。
- ADMIN 不能改派自己的申請，要由另一位 ADMIN 操作。
- 改派後原審核人失去讀取與處理權。

**重複提交**：
- 每個新申請帶 `requestId`。同員工＋同 `requestId` 唯一。
- 相同內容重送：回傳原申請，沿用原狀態與原審核人，不新增也不重建。
- 不同內容：409。

## 6. 不變條件

1. 同一員工的 PENDING／APPROVED 申請時段互不重疊。
2. 申請的審核人不是申請人（資料庫 CHECK）。
3. 狀態只能從 PENDING 轉出；終態不再改變。
4. 同員工＋同 `requestId` 最多一筆（資料庫唯一限制）。
5. 每次狀態改變、改派、指定設定修改都有一筆歷程，與業務修改同成同敗；歷程只新增。
6. 申請人由登入身分決定；核准／退回者必須是送出當下保存（或改派後）的審核人。

## 7. 明確不做

假別額度、年資、薪資、扣薪、法規計算；排班、國定假日、午休扣除；自動修改出勤或工時；多關簽核、代理人、通知、附件、流程設計器；已核准申請的取消或改單；跨重新整理的草稿保存；雲端、HTTPS、部署、多租戶、重構；T06。
