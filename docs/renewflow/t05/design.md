# Design：T05 狀態、鎖與重複提交

## 1. 狀態機

```
            送出（申請人）
                 │
                 ▼
  ┌──────────► PENDING ◄──────────┐
  │   改派（ADMIN，版本 +1）       │
  └───────────────┘
      │              │              │
 核准（審核人）   退回（審核人，原因必填）   撤回（申請人）
      ▼              ▼              ▼
   APPROVED       REJECTED       WITHDRAWN      ← 終態，不再改變
```

所有轉移都用條件 UPDATE：`where id = ? and version = ? and status = 'PENDING'`。即使鎖被移除，也不可能從終態被改回來（第二道防線）。

## 2. requestId、版本號、交易鎖各自解決什麼

| 機制 | 解決的問題 | 解決不了的 |
|---|---|---|
| `requestId`（同員工唯一） | 同一次提交因網路不明而重送 → 只會有一筆；內容不同 → 409，不覆寫 | 兩次**不同**的提交時段重疊 |
| 版本號 `expectedVersion` | 依據過期畫面的操作（例如對方已撤回、已改派）→ 409，不覆蓋 | 跨多筆的規則（重疊、審核人有效性） |
| `OrganizationLock` | 讀取 → 檢查 → 寫入期間不被插隊：重疊、審核人仍有效、操作者仍有效、與停用／改角色的先後 | — |
| 條件 UPDATE、唯一限制、CHECK | 最後防線：鎖被誤刪時仍擋住重複 requestId、自審、終態改變 | 重疊（沒有資料庫限制，見 D-73） |

## 3. 送出流程（鎖內順序）

1. 正規化輸入（鎖外，純計算）。
2. `acquireFor(actor)`：取鎖，重新確認操作者。
3. 查同員工＋同 requestId：
   - 有 → 比對正規化內容（假別、日期、起訖、原因）：相同 → 回傳原申請（`replayed`）；不同 → 409。不重新判斷審核人或重疊。
4. 決定審核人（指定 → 直屬主管 → 無）；無效 → 409 `NO_VALID_APPROVER`。
5. 重疊查詢 → 409 `LEAVE_OVERLAP`。
6. `INSERT … ON CONFLICT DO NOTHING RETURNING id`（同 requestId 的最後防線）。
7. 歷程 `SUBMITTED`。

## 4. 改派、核准、撤回的競爭

全部在同一把鎖內，依先後執行。後到的操作讀到的是最新狀態：
- 核准 vs 撤回：先到的成功，後到的得到 409 `LEAVE_NOT_PENDING`。
- 核准 vs 改派：先改派 → 原審核人的核准讀到 `approver_id` 已換人 → 404；先核准 → 改派得到 `LEAVE_NOT_PENDING`。
- 審核人被降級 vs 審核：先降級 → 審核人的請求在取鎖後重新確認帳號 → 401；先審核 → 降級照常。

## 5. 前端：結果不明的提交

沿用 T04 第 2 輪的原則（`TimesheetPage`）：
- 提交內容與 requestId 綁定；送出期間鎖住表單。
- 網路錯誤、5xx、回應遺失 → 保存「未確認快照」，表單鎖定，只能「重新送出原內容」（同 requestId、同內容），或在看過警告後明確「放棄追蹤」。
- 重試被拒絕（403、409…）不代表原提交不存在，快照保留。
- 200 `replayed` 或 201 → 確認建立，換新 requestId。
- 第一次提交就被明確拒絕（400／409）→ 保留輸入讓使用者修改。
- 401 → 既有登入失效流程，表單卸載，不會換帳號重送。
- 不跨重新整理保存；畫面提示重新整理後請先查看清單確認。

## 6. 指定審核人與組織的關係

`leave_approver_setting` 獨立於 `employee.manager_id`。Max → Iris 只影響「Max 的請假誰審核」，Max 仍沒有直屬主管，Iris 的主管仍是 Max，組織沒有循環。
