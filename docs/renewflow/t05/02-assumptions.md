# T05：假設與決策

以下是本批的工程假設與 STMAX 示範規則，**不是正式人事制度，也不宣稱符合法規**。

## 假設

| 編號 | 內容 | 理由 |
|---|---|---|
| A-80 | 假別固定三種：事假 `PERSONAL`、病假 `SICK`、特休 `ANNUAL`；沒有額度 | 授權範圍；額度與年資明確不做 |
| A-81 | 日期可為過去、今天、未來，但限制在今天（台北）前後 365 天內 | 允許病假補申請；擋下明顯打錯的年份 |
| A-82 | 半小時刻度；結束 > 開始；不跨午夜，所以最晚結束是 23:30（`time` 無法表示 24:00） | 最小可操作版本；跨日分開送出 |
| A-83 | 有指定審核人但它已無效時，**拒絕送出**而不是退回採用直屬主管 | 指定設定代表管理員的明確意圖；靜默改用主管可能讓不該審的人審核 |
| A-84 | 撤回原因選填；退回與改派原因必填；核准不需原因 | 授權範圍只要求退回與改派必填 |
| A-85 | 審核人能看到「指派給自己的」所有狀態的申請（含已處理）；改派後原審核人看不到 | 「只能讀取被明確指派給自己的申請」；處理過的仍是指派給自己的 |
| A-86 | 清單：狀態篩選＋日期範圍（同時提供或都不提供，最多 366 天）＋分頁（預設 20、最多 50） | 合理上限 |
| A-87 | 申請時段長度只是「開始到結束的分鐘數」，未扣除休息時間 | 沒有排班與午休規則；畫面明示 |
| A-88 | 沒有草稿狀態（與指南原始描述不同，見需求文件第 2 節） | 授權範圍 |

## 決策

| 編號 | 決策 | 理由 | 未採用 |
|---|---|---|---|
| D-70 | 請假寫入（送出、核准、退回、撤回、改派、指定設定）**共用 `OrganizationLock`**，取鎖後才讀取帳號、組織、設定、申請 | 審核人是否有效、是否為主管，依賴組織資料；與「停用、改角色、改主管」放在同一條隊伍，先後關係清楚。重疊檢查也因此安全 | 每位員工一把列鎖：無法同時保護「審核人被停用 vs 審核」；只靠版本或先查再寫：重疊與並行核准都會出錯 |
| D-71 | 取鎖後**重新確認操作者**仍存在、啟用、角色與 Session 快照相同；失效 → 401 `UNAUTHENTICATED`、不寫任何資料 | 請求通過 Filter 後可能等鎖；等待期間被降級或停用，不能再用舊權限操作。下一個請求由 `ActiveAccountFilter` 作廢 Session；資料庫故障維持 500 | 只靠 Filter：有等待鎖的時間窗 |
| D-72 | 同樣的取鎖後檢查也套用到 T05 前置的組織寫入 | 同一把鎖、同一個時間窗；結果「最後一位 ADMIN」改由這一步先擋下（舊身分 → 401），LAST_ADMIN 檢查保留為第二道防線 | 只套用請假：組織寫入留下相同漏洞 |
| D-73 | 重疊由「鎖內查詢」保證，不用 PostgreSQL 排除限制（`EXCLUDE USING gist`） | 員工欄位的等值比較需要 `btree_gist` 擴充；要在 migration 建立擴充並確認測試庫 clean 的行為，超出本批；所有寫入已在同一把鎖內 | 排除限制：資料庫層最強，但需擴充 |
| D-74 | `requestId` 重送：內容相同 → 200＋`replayed: true` 回傳原申請；不同 → 409 `REQUEST_ID_CONFLICT` | T04 曾出現 requestId 與內容不一致；這次明確比對正規化內容 | 一律 409：前端要再查一次才能確認 |
| D-75 | 存取不到的申請（他人、非指派、改派後）一律 404 `LEAVE_NOT_FOUND` | 不洩漏「這筆存在」；與不存在無法區分 | 403：會洩漏存在與否 |
| D-76 | 指定請假審核人是獨立的表（`leave_approver_setting`），不寫 `employee.manager_id` | Max → Iris 若寫成主管關係，會與 Iris → Max 形成組織循環 | 共用主管欄位：違反組織不變條件 |
| D-77 | 歷程沿用只新增觸發器；前後值放在明確欄位（狀態、審核人 ID），不用 JSON | 欄位固定、可以用外鍵確保 ID 有效 | JSON：本批欄位少，不需要 |
