# T03.3 架構、資料、API、安全與設計

## 架構／Proposal

沿用模組化單體與 Controller → Service → Repository、DTO、建構子注入。不新增套件。沿用組織鎖作為跨模組權限變更序列化基礎；新增出勤規則元件集中跨列合法性與員工列鎖，避免各寫入路徑各自實作不一致。

## 資料模型

V8 只移除每日有效唯一索引，新增「員工＋日期、有效且未完成」部分唯一索引。attendance 原資料與所有外鍵不變。新增 attendance_clock_submission，主鍵為員工＋UUID，保存動作、有效本文指紋、出勤 ID、成功回應快照。出勤、事件與去重資料同交易。V1～V7 不修改。

## 鎖順序／Security Design

出勤寫入：組織 advisory lock → 員工列 FOR NO KEY UPDATE → 定位設定 FOR SHARE（僅新打卡）→ 申請／出勤／事件／去重／歷程。先取組織鎖再重新確認登入者角色及啟用狀態。工時僅員工列 → 專案共享鎖，沒有回頭取得組織鎖；定位管理僅定位設定鎖與事件外鍵（KEY SHARE），與 NO KEY UPDATE 相容。避免逆向循環。代價是出勤寫入會和組織／請假寫入排隊，效能未做負載驗證。

更正、補登、核准、作廢一律在同鎖同交易中查其他有效時段、檢查與寫入。時間區間採相鄰允許的邊界比較；未完成視為向後延伸。未完成時段必須是當日最後時段。版本條件更新仍保留。權限、資料隔離、自審／自改禁止不放寬。

## API Design

POST clock-in／clock-out 本文必須有 requestId(UUID)，其他定位欄位沿用原契約。下班另須 expectedAttendanceId＋expectedVersion，原請求尚未成功但目標被更正或換組時拒絕，不能關閉新組。無本文／缺識別碼回 400。打卡成功 DTO 回傳相同 requestId，前端驗證此識別碼；一般紀錄查詢的 requestId 為 null。相同員工同鍵同有效本文回原成功 DTO；異內容或異操作 409 CLOCK_REQUEST_MISMATCH。不回傳其他人的定位。指紋保存原提交的定位值；不需要定位時事件不保存座標。

今日 DTO 新增 records（所有時段含作廢）與 completedSeconds（有效完成時段的秒數合計，微秒精度運算後才截為秒）。舊單筆欄位表示目前未完成時段，若無則最後有效時段，用於過渡；COMPLETED 表示已有完成時段且可再次上班。

前端保存當次掛載的原本文與 requestId；未知結果只手動重送原本文或經警告明確放棄。切頁取消未送操作；已送結果不更新新頁。重新整理不持久化追蹤與座標，重進頁查真實資料，不自動重送。更正與今日申請明確選目標組。

工時成功契約為 EntryResponse（無 requestId），驗證正整數 ID、版本、專案結構、原提交日期／專案／分鐘／內容及時間欄位。DUPLICATE_SUBMISSION 需有效本人 entryId 才確認原提交已存在。成功本文例外在工時 API 邊界轉成未知結果，不更動共用 HTTP 與既有請假行為。
