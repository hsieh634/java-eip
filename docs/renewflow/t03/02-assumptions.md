# T03 學習假設登錄

以下是**本機學習規則**，不宣稱符合任何正式公司的人事制度。

| 編號 | 假設 | 影響 |
|---|---|---|
| A-07 | 業務時區固定為 Asia/Taipei | 業務日期換算 |
| A-08 | 打卡時間一律由後端伺服器的 `Clock` 決定，前端無法指定 | 防止偽造時間 |
| A-09 | 每位員工每個業務日期最多一筆出勤（一組上下班） | 唯一限制 |
| A-10 | 必須先上班才能下班；已下班後當天不能再開第二組 | 狀態規則 |
| A-11 | 不支援跨日班、輪班、補登、修改或刪除出勤 | 範圍界線 |
| A-12 | 昨日（或更早）未下班的紀錄保留為未完成並顯示提醒，不自動補下班 | 資料真實性 |
| A-13 | 今日仍可建立新紀錄；下班只處理「今日」紀錄，不替昨日補登 | 狀態規則 |
| A-14 | 伺服器時鐘被視為正確；若時鐘倒退導致下班時間早於上班時間，視為系統錯誤（5xx）而不是業務衝突 | 錯誤分類 |

## 決策紀錄（T03）

| 編號 | 決策 | 原因 | 替代方案與成本 |
|---|---|---|---|
| D-14 | 上班用 `INSERT ... ON CONFLICT DO NOTHING`，以回傳筆數判斷 | 唯一限制是最終裁判；衝突不產生例外，因此**交易不會進入失敗狀態**，同一交易內還能繼續查詢並回報原因 | 捕捉 `DataIntegrityViolationException`：PostgreSQL 在錯誤後會中止整個交易，需要新交易才能再查詢，且會把「重複」與其他完整性錯誤（例如外鍵）混在一起 |
| D-15 | 下班用條件更新 `WHERE clock_out_at IS NULL` | 單一原子語句；第二個並行請求會等第一個提交，再以最新資料重新判斷條件而更新 0 筆，不會覆蓋第一次的下班時間 | 悲觀鎖（`SELECT ... FOR UPDATE`）：多一次往返；樂觀鎖（`@Version`）：衝突時需要重試或拋例外，對「只允許寫一次」的欄位較繞 |
| D-16 | 所有受保護請求經過共用 Filter 查詢最新帳號狀態 | 停用／刪除／角色變更立即生效，不必每個 Service 記得檢查 | 每個 Service 入口各自檢查：容易漏；快取狀態：停用生效延遲 |
| D-17 | 前端以 hash（`#/attendance`）切換畫面，不引入路由套件 | 只有兩個畫面，hash 即可支援重新整理與瀏覽器上一頁 | react-router：T04 起畫面更多時再評估 |
| D-18 | E2E 寫入測試在「隔離堆疊」進行：另一個後端（8081、測試資料庫）、另一個 Vite（5174）、每次新建專用員工 | 不碰使用者的開發帳號與出勤，也不需要清空資料即可重跑 | 對開發庫寫入並清理：違反隔離要求 |
