# Design：T05 前置——鎖、交易與狀態

> **T05 前置子任務**。

## 1. 為什麼版本號不夠

版本號（`expectedVersion`）只保證「我依據的那一筆，送出時還是同一版」。組織規則跨越多筆：

| 情境 | 兩個請求改的列 | 各自版本 | 合起來的結果 |
|---|---|---|---|
| A 的主管設為 B，同時 B 的主管設為 A | A、B 兩列 | 都正確 | 循環 |
| 兩位 ADMIN 同時把對方降級 | 兩列 | 都正確 | 沒有 ADMIN |
| 停用部門 D，同時把員工 E 指派到 D | 部門 D、員工 E | 都正確 | 停用部門裡有啟用員工 |
| 停用主管 M，同時把 E 的主管設為 M | M、E | 都正確 | 主管已停用 |

每個請求單獨檢查時都「看起來合法」：這是典型的 check-then-act 競態。

## 2. 鎖策略（D-60）

**所有組織寫入交易的第一個動作**：`select pg_advisory_xact_lock(7050001)`。

| 項目 | 說明 |
|---|---|
| 範圍 | 部門建立／修改、員工建立／修改、dev 示範組織初始化。**T05 起擴大**：請假寫入（送出、核准、退回、撤回、改派）與指定請假審核人設定也取同一把鎖，取鎖後並重新確認操作者（見 [`../t05/02-assumptions.md`](../t05/02-assumptions.md) D-70～D-72）。**不含**登入、打卡、工時、清單與歷程查詢 |
| 順序 | 先取組織鎖，之後才讀取與寫入任何員工或部門列；只有這一把，所以不會有鎖順序造成的死結 |
| 釋放 | 交易提交或回滾時自動釋放（transaction-level），不會忘記解鎖 |
| 一致性 | PostgreSQL 預設 READ COMMITTED：取得鎖之後的每個查詢都看得到前一個持鎖交易已提交的結果 |
| 代價 | 組織寫入彼此排隊；管理員操作頻率低，可以接受 |
| 防呆 | `OrganizationLock.acquire()` 標 `Propagation.MANDATORY`：沒有交易就呼叫會直接失敗 |

為什麼不用其他作法：

- **SERIALIZABLE**：衝突時資料庫丟序列化錯誤，要寫重試；規則較難推理。
- **對相關列 `SELECT … FOR UPDATE`**：要事先知道整條主管鏈、所有 ADMIN、部門下所有員工，還要固定加鎖順序，容易漏。
- **分散式鎖、新套件**：本專案是單一資料庫，不需要。

## 3. 每個寫入的檢查順序

| 寫入 | 鎖內的檢查（依序） |
|---|---|
| 建立部門 | 代碼唯一（`ON CONFLICT DO NOTHING`） |
| 修改部門 | 存在 → 版本 → 有變更 → 狀態變更需原因 → 停用時無啟用員工 |
| 建立員工 | 部門存在且啟用 → 主管存在且為啟用 MANAGER／ADMIN → 員工編號／帳號唯一 |
| 修改員工 | 存在 → 版本 → 有變更 → 需原因 → 自己 → 部門（新指派須啟用；重新啟用時部門須啟用）→ 主管（非自己、有效、不循環）→ 有部屬不可停用／降成 EMPLOYEE → 最後 ADMIN |

通過後才執行版本條件 UPDATE（`version = version + 1`），並在同一交易寫入歷程。歷程寫入失敗 → 例外 → 整筆回滾（`OrganizationAuditRollbackIntegrationTest`）。

## 4. 員工狀態

```
          建立（啟用）
              │
              ▼
   ┌──── 啟用 ◀────────────┐
   │      │                 │ 重新啟用（部門須啟用，或同時改派／移除）
   │ 停用（不可是自己；     │
   │ 不可有部屬；           │
   │ 不可是最後的 ADMIN）   │
   │      ▼                 │
   └──── 停用 ──────────────┘
```

角色可在三種之間改；改成 EMPLOYEE 時不可有部屬；ADMIN 不可改自己的角色；不可讓啟用 ADMIN 變成零。

## 5. 版本變化

| 動作 | department.version | employee.version |
|---|---|---|
| 建立 | 0 | 0 |
| 每次成功修改 | +1 | +1 |
| 被拒絕的修改（任何 4xx） | 不變 | 不變 |
| dev 示範初始化（有補欄位） | 不變（新建為 0） | +1 |
| dev 示範初始化（已符合） | 不變 | 不變 |

## 6. 前端的衝突處理

- 修改對話框以開啟時的資料（含 `version`）為基準。
- 409 `EMPLOYEE_CHANGED`／`DEPARTMENT_CHANGED`：對話框保持開啟、輸入保留，顯示說明與「載入最新資料（會取代目前輸入）」按鈕；只有使用者按下才會換成最新內容，不自動重送。
- 其他錯誤：顯示後端訊息，輸入保留。
- 停用或改角色時，送出前先提示「這位員工目前的登入會失效」。
