| A-77 | 部門的啟用狀態變更必填原因；名稱修改不必 | 與員工「狀態類變更必填原因」一致 | — |

## 決策

| 編號 | 決策 | 理由 | 未採用 |
|---|---|---|---|
| D-60 | **所有組織寫入交易一開始取得同一把 PostgreSQL 交易級 advisory lock**（`pg_advisory_xact_lock`，固定鍵），之後才讀取並檢查 | 主管循環、最後 ADMIN、部門停用 vs 指派這些跨多列的規則，必須在「讀取 → 檢查 → 寫入」期間沒有其他組織寫入插隊；管理員操作頻率低，排隊成本可忽略；交易結束自動釋放；登入、打卡、工時不取這把鎖 | 只靠版本號：只能擋同一筆的過期表單（見 D-61）；SERIALIZABLE：衝突時要重試；鎖住多列 `FOR UPDATE`：要事先知道整條主管鏈與所有 ADMIN，順序難以固定 |
| D-61 | 版本號只用來偵測「同一筆資料的過期表單」 | 例：A→B 與 B→A 同時修改的是**不同**兩筆員工，各自版本都正確，但合起來形成循環；兩位 ADMIN 互相降級也是修改不同兩筆 | — |
| D-62 | 組織寫入一律用原生條件式 SQL（版本條件 UPDATE、`ON CONFLICT DO NOTHING RETURNING id`）；`Employee` Entity 的新欄位對 JPA 唯讀 | 與 T03～T04 一致；避免其他地方的 JPA `save` 意外覆寫組織欄位 | JPA 自動寫回：可能繞過版本條件 |
| D-63 | 歷程的前後值以 JSON 文字存在單一欄位 | 一次操作可能同時改多個欄位；只用於顯示，不做查詢條件 | 每欄一列：要另外分組；`jsonb`＋Hibernate JSON 對應：需確認與 Jackson 3 的整合，超出本批 |
| D-64 | 主管循環檢查：從「新主管」沿著主管鏈往上走，遇到自己就是循環（最多走員工總數步） | 在組織鎖內進行，鏈不會在檢查期間被改；資料庫另有「不可自指」CHECK | 遞迴 CTE：可行但較難閱讀；觸發器：邏輯分散 |
| D-65 | STMAX 組織初始化是**另一個開關**（`RENEWFLOW_DEMO_STMAX_ORG_ENABLED`），預設關閉 | 帳號初始化與組織安排可分開啟用；已建帳號的使用者不會因升級就被自動改組織 | 併入帳號初始化：升級後重啟就自動改資料 |
| D-66 | 示範初始化：帳號或員工編號不符、**別人建立的**同代碼部門名稱不同或已停用 → **整批停止**；由示範初始化建立的部門（有 `SYSTEM_DEMO_SEED` 的建立歷程）之後被改名或停用仍沿用、不改回；個別員工已有不同部門／主管 → 保留並回報，空白的欄位照常補上 | 前者會讓整個安排失去意義；後者是使用者自己改過的設定，不能覆寫 | 全部覆寫：違反需求 |
| D-67 | 系統初始化的歷程 `source = SYSTEM_DEMO_SEED`、操作者為空 | 不偽造 Max 的人工操作 | 記成 Max：誤導稽核 |
| D-68 | 曾被管理員調整過組織資料的員工（有 `source = ADMIN` 的歷程），示範初始化**整個人不動**、只回報 | 「只補空白欄位」不足以保護使用者：例如管理員刻意移除 Mia 的主管，重啟時若只看「主管是空的」就會補回去，等於改回使用者的調整 | 只看欄位是否為空：重啟會覆寫刻意清空的設定 |
| D-69 | 測試設定的連線池常駐連線降為 2、閒置 10 秒釋放（上限仍 10） | 新增的測試 Context 讓全套測試的常駐連線超過 PostgreSQL `max_connections = 100`（開發後端另占 10），實際出現 `too many clients already`；上限不變，並行測試可用的連線數不變 | 降低上限：會削弱並行測試；提高資料庫上限：要改容器設定 |
