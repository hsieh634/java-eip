# T04 假設與決策

以下是 **T04 第一版的工程假設，不是公司正式的人事制度**。

## 使用者確認的假設

| 編號 | 內容 |
|---|---|
| A-50 | 業務日期沿用 Asia/Taipei |
| A-51 | 可以填今天或過去的日期，不可填未來日期 |
| A-52 | 同一天可以填多個專案；同一專案也可有多筆不同工作紀錄 |
| A-53 | 每筆最少 15 分鐘，以 15 分鐘為單位 |
| A-54 | 每人每日所有紀錄合計不得超過 24 小時 |
| A-55 | 24 小時是資料合理性上限，不代表正常工時或加班規則 |
| A-56 | 工時與出勤打卡是不同資料：不以是否打卡、打卡時長或定位結果限制填報 |
| A-57 | 沒有打卡、人在公司外或定位失敗，仍可填工時 |
| A-58 | 所有有效使用者都可選擇啟用專案，尚不限制專案成員 |
| A-59 | 過去紀錄可以修改，不設月份關帳或補填期限 |

## 本階段補充的假設與決策

| 編號 | 內容 | 理由 | 未採用 |
|---|---|---|---|
| D-40 | 工時以整數分鐘保存（`integer`），畫面輸入小時、前端以整數運算換算 | 浮點數無法精確表示 0.1 等十進位小數，加總會累積誤差；整數分鐘可精確比較與加總 | `double` 小時：1.1 + 2.2 ≠ 3.3；`numeric(4,2)` 小時：可行，但「15 分鐘倍數」與上限比較不如整數直覺 |
| D-41 | 每日上限以「鎖住員工列（`FOR NO KEY UPDATE`）」序列化同一人的寫入，再於同一交易內加總、檢查、寫入 | 跨多列的合計無法用 CHECK 或唯一限制表達；只鎖單一員工列，不同員工互不影響；NO KEY UPDATE 不會擋到其他表引用該員工的外鍵檢查 | SERIALIZABLE：衝突時需重試；全域鎖：所有人排隊；只靠前端加總：可被繞過 |
| D-42 | 工時寫入以 `FOR SHARE` 鎖住目標專案；停用是一般的版本條件 UPDATE | 停用與新增有明確先後：先取得專案的新增會完成並保留，停用先完成則後續新增被拒 | 只讀專案狀態不加鎖：讀完到寫入之間可能被停用 |
| D-43 | 鎖定順序固定：員工列 → 專案列 → 工時列 | 所有寫入路徑一致，避免死鎖；管理員修改專案只鎖專案列，永遠不等員工列 | — |
| D-44 | 重複新增以「員工＋requestId」唯一限制＋`INSERT … ON CONFLICT DO NOTHING RETURNING id` 處理；重複時回 409 附本人紀錄 ID | 不讓交易失效、不靠捕捉例外；不以「日期＋專案＋內容」判斷重複（使用者可能合法記錄相同工作） | 捕捉唯一限制例外：PostgreSQL 交易會失效；內容比對：誤判合法紀錄 |
| D-45 | 他人或不存在的工時一律回 404 `TIMESHEET_NOT_FOUND` | 不洩漏他人紀錄是否存在（與 T03.1 申請的策略一致） | 403：等於告訴對方「這筆存在，只是不是你的」 |
| D-46 | 專案代碼建立後不可修改；修改端點的本文沒有 `code` | 代碼是對外識別，改了會讓既有工時的意義混淆 | 允許修改：需另外處理歷史顯示 |
| D-47 | 修改與目前完全相同時回 400（專案與工時皆是） | 不產生無意義的版本遞增 | 照常更新：版本無故改變，造成其他分頁不必要的衝突 |
| D-48 | 全域關閉 Jackson 的「小數轉整數」（`accept-float-as-int: false`） | 原本 `minutes: 90.5` 會被默默截斷成 90，違反「不把不合法值變成合法值」；測試抓到後改為 400 | 只在工時 DTO 自訂反序列化：其他整數欄位仍有同樣問題 |
| D-49 | 不使用 `@ManyToOne`，以外鍵 ID 表示關聯，顯示專案名稱時批次查詢 | 本階段只需要 ID；避免延遲載入、N+1 與序列化 Entity 的問題 | `@ManyToOne(fetch = LAZY)`：需要額外理解代理物件與交易範圍 |
| D-50 | `DateRange`（31 天、預設本月）改為 public，由工時共用 | 規則與出勤查詢一致，不重寫一份 | 複製一份：規則可能分歧 |
| D-51 | 專案變更不另建歷程表 | 需求未要求；版本與 updatedAt 已能偵測與顯示最後修改 | 建立歷程：超出本階段範圍 |
