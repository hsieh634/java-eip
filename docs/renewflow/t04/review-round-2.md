## 1. 問題

### R1-A：重試失敗抹除了原提交的不確定性
1. 新增 90 分鐘，後端已建立，但回應遺失 → 前端進入「結果不明」，保留快照與 requestId。
2. 按「重新送出原內容」，這次收到 403（例如 CSRF 驗證失敗）。
3. 舊程式把它當成「明確拒絕」：清除快照、回到可編輯。
4. 使用者改成 120 分鐘再送（同一個 requestId）→ 後端回 `DUPLICATE_SUBMISSION` → 前端清空表單；實際資料仍是 90 分鐘。

**原則：重試被拒絕，只說明「這一次請求」被拒絕，不能證明先前結果不明的那一次沒有成功。**

### R1-B：啟用專案清單為空時，無法確認原提交
送出按鈕會因「沒有啟用專案」而停用。原提交結果不明時，若管理員停用最後一個專案、員工更新清單，就按不到「重新送出原內容」。

## 2. 需求

| 編號 | 需求 |
|---|---|
| N-1 | 新增一旦進入「結果不明」，就記住「這筆邏輯提交尚未確認」（未確認快照），直到**確認建立**或**使用者明確放棄**才清除 |
| N-2 | 重試期間（送出中）不得遺失「這是未確認提交的重試」這件事 |
| N-3 | 未確認期間的任何重試失敗（403、404、409 專案停用、409 每日上限、400、網路、5xx）：保留快照、requestId 與鎖定；離開 loading；顯示「本次失敗原因」與「原提交結果仍未確認」 |
| N-4 | 使用者可再次手動重試（同一份快照），或經既有警告流程明確放棄；不自動重試 |
| N-5 | 重試成功（201）或 `DUPLICATE_SUBMISSION`：確認原提交，沿用現有完成流程 |
| N-6 | 從未進入結果不明、首次送出就被明確拒絕（每日上限、欄位、專案停用）：仍可修正後再送（不永久鎖定） |
| N-7 | 401：沿用既有登入失效處理（回登入頁，表單隨之卸載）；不允許跨帳號重送 |
| N-8 | 確認原提交不受「沒有啟用專案」限制：有完整未確認快照時，即使清單為空也可重試；重試只用快照，不依下拉選單重組、不換專案或 requestId |
| N-9 | 可編輯狀態（新增模式）且沒有啟用專案：仍禁止送出新工時 |
| N-10 | 提示文字不互相矛盾：未確認期間清單為空時，說明「不能新增新工時，但可以確認上一筆提交」 |
| N-11 | 保留卸載後不處理舊回應、防連按；「修改既有停用專案紀錄」規則不變 |

採保守策略：未確認期間的失敗一律不解鎖。不新增查詢 API、不做持久化草稿。

## 3. 狀態轉移（新增模式）

| 目前狀態 | 事件 | 修正前 | 修正後 |
|---|---|---|---|
| 可編輯 | 送出 → 201 | 完成（新表單） | 同左 |
| 可編輯 | 送出 → 明確拒絕（400／404／409） | 可編輯（顯示原因） | 同左（N-6） |
| 可編輯 | 送出 → 網路錯誤、回應遺失、5xx | 結果不明（鎖定、保留快照） | 同左 |
| 結果不明 | 重新送出原內容 → 201 或 `DUPLICATE_SUBMISSION` | 完成（確認建立） | 同左（N-5） |
| 結果不明 | 重新送出原內容 → 403／400／404／409 | **可編輯（清除快照）** ← R1-A | **仍是結果不明**：快照、requestId、鎖定保留；顯示本次原因與「仍未確認」（N-3） |
| 結果不明 | 重新送出原內容 → 網路錯誤／5xx | 結果不明 | 同左 |
| 結果不明 | 重新送出原內容 → 401 | 回登入頁 | 同左（N-7） |
| 結果不明 | 啟用專案清單變空 | **無法按重新送出** ← R1-B | 仍可重新送出原內容（N-8） |
| 結果不明 | 放棄追蹤 → 警告 → 確定 | 新表單（新的 requestId） | 同左 |
| 可編輯 | 沒有啟用專案 | 送出停用 | 同左（N-9） |

「送出中」是請求進行的暫時狀態；修正後它只負責鎖定與防連按，**是否為未確認提交的重試由「未確認快照是否存在」決定**，不會因暫時切換而遺失。

## 4. 驗收（`frontend/e2e/timesheets-retry-boundaries.mjs`，`npm run e2e:timesheets-retry`，隔離堆疊）

| 編號 | 情境 | 預期 |
|---|---|---|
| A | 原提交成功、回應遺失（先以 API 確認後端已建立）→ 第一次重試 403 → 再次重試 | 403 後離開 loading 但仍鎖定；日期、專案、分鐘、內容、requestId 不變；修改嘗試不被接受；再次重試的 payload 與原提交完全相同；最後只有一筆 90 分；不誤報新內容；之後可用修改流程改成 120 分 |
| B | 原提交未到達後端（網路失敗）→ 專案被停用 → 重試得 `PROJECT_INACTIVE` | 保留快照與未確認狀態、同一 requestId、沒有建立任何紀錄；可透過警告明確放棄，之後的新提交使用新的 requestId |
| C | 原提交成功、回應遺失 → 啟用專案清單變空 | 快照仍在；「重新送出原內容」可按；確認建立、只有一筆；確認後的新表單因沒有專案而停用送出 |
| D | 原有修正路徑 | `timesheets-review.mjs`（首次明確拒絕可修正、R2 草稿保留、放棄警告與新 requestId）與 `timesheets.mjs` 全部通過；沒有未處理的 Promise 拒絕、沒有卡住的 loading |
