## 1. 為什麼要同時比對 ID＋版本（R1）

### 原本的問題
舊的直接更正請求只有 `employeeId、workDate、expectedVersion`。後端先查「該日目前的有效紀錄」，再用 `UPDATE ... WHERE id = <查到的 id> AND version = ?`。

時間線：

1. 管理員甲打開紀錄 A 的更正對話框（A 的版本 = 1）。
2. 管理員乙作廢 A。
3. 員工重新上班、下班，產生新紀錄 B：上班 → 版本 0，下班 → 版本 1。
4. 甲送出舊對話框：後端查到的「當日有效紀錄」是 B，B 的版本剛好也是 1 → **B 被改掉**。

版本號碼只在「同一筆紀錄」裡有意義，它回答「這一筆有沒有被改過」，但回答不了「是不是同一筆」。兩筆不同紀錄的版本相同是正常的（每筆都從 0 開始數）。

### 修改後
- 請求新增 `attendanceId`。更正＝`attendanceId`＋`expectedVersion` 都帶；補登＝兩者都不帶；只帶其一 → 400。
- 後端用前端帶來的 ID 查：必須存在、屬於該員工、日期相同、仍有效、版本相同，否則 409 `RECORD_CHANGED`。
- 最終仍用 `correctIfCurrent(id, version, ...)` 這個原子條件更新（`WHERE id = ? AND version = ? AND voided_at IS NULL`），擋住「查詢之後、更新之前」的並行變動。**ID 從頭到尾不會被替換。**

位置：`AttendanceAdminService.correctDirectly`；前端 `AdminAttendancePage.tsx` 的 `DirectCorrectionDialog` 送出 `attendanceId: record.id`。

### 同樣的想法用在員工申請（表單快照）
員工打開「撤銷下班」「整組作廢」「更正／補登」表單時，前端記住看到的 `recordId＋version`（今日查詢 `/api/attendance/me/today` 現在會回傳這兩個欄位）。送出時一起帶上：

- 兩者都有：當日有效紀錄必須正是那一筆、那個版本。
- 兩者都 null：表示表單看到「沒有紀錄」，現在也必須沒有。
- 不一致 → 409 `RECORD_CHANGED`，**不建立申請**。

這是「提出時」的檢查；「核准時」還有原本的檢查（申請保存的目標 ID／版本，不符 → `REQUEST_STALE`）。兩道檢查各擋不同時間點的變動。

## 2. 撤銷下班 vs 整組作廢：資料上差在哪

| | 撤銷下班打卡 | 整組作廢並重新打卡 |
|---|---|---|
| 申請內容 | `CORRECT_TIME`：希望上班＝目前上班（完整精度）、希望下班＝null | `RESET_TODAY` |
| 何時可申請 | 今日有效紀錄已有下班 | 今日有有效紀錄（只有上班也可以） |
| 核准後的 `attendance` | **同一列**：`clock_out_at = null`、`version + 1`、`corrected_at` 有值 | 舊列 `voided_at` 有值（保留原時間）、`version + 1`；今日沒有有效紀錄 |
| 今日狀態 | WORKING，可再按下班 | NOT_STARTED，要重打上班與下班 |
| 紀錄列表 | 仍只有 1 筆 | 作廢 1 筆＋之後重打的有效 1 筆 |
| 歷程 `requestKind` | `REVOKE_CLOCK_OUT`，修改後是時間 | `RESET_TODAY`，修改後是「整組作廢」 |
| 跨過台北日期 | 仍可核准（就是一般的更正） | 不可核准（`RESET_DATE_PASSED`） |

為什麼撤銷下班不新增一種申請類型？`CORRECT_TIME` 已經完整支援「核准前不改、核准時比版本、過時拒絕、寫歷程」，撤銷下班只是它的一個特例。新增類型要改 V3 的檢查條件（得加新 migration）。所以後端依內容判斷 `kind`（`AttendanceViews.kindOf`）：原本有上下班、希望下班為空、希望上班等於原上班 → `REVOKE_CLOCK_OUT`。

**完整精度**：資料庫存到微秒（例如 `12:26:23.631575`），畫面只顯示到秒。如果送 `12:26:23`，核准時上班時間會被悄悄改掉 0.63 秒，而且「上班時間不變」這個承諾就破了。前端 `toPreciseTimeValue` 從後端回傳的字串取出小數秒（JavaScript `Date` 只到毫秒，不能用它轉）。更正表單與管理員對話框也一樣：**沒改動的預填值**送出原值的完整精度（`submittedTime`）。

不提供「只取消上班、保留下班」：有效紀錄不允許「沒有上班卻有下班」（V2 的檢查條件）。

## 3. React 的 key／effect 如何影響「重新查詢」（R2）

`useLoad(loader, key)` 的 effect 依賴 `[key, tick, ...]`：

```ts
useEffect(() => { /* 呼叫 loader，active 旗標丟棄過期回應 */ }, [key, tick, enabled, refresh])
```

原本 `key = "員工|起日|迄日"`。按「查詢」只做 `setApplied({ employeeId, from, to })`。條件沒變時 key 字串也一樣，React 比對依賴陣列後**不會重跑 effect**，畫面停在舊資料。新物件雖然讓元件重新 render，但 effect 只看依賴值。

修正：`applied` 多一個 `seq`，每按一次 +1，key 變成 `"員工|起日|迄日|seq"`。

- 相同條件 → key 不同 → effect 重跑 → 重新請求。
- 舊的請求在 cleanup 時 `active = false`，晚到的回應被丟棄（與切換條件時相同）。
- `stored.key !== key` 時 state 視為 loading，所以不會把舊結果當新結果顯示；錯誤與「重試」沿用 `reload`。

為什麼不在「條件相同」時改呼叫 `reload()`？那會變成兩條路徑（新條件走 key、相同條件走 tick），每次修改都要記得兩邊；用一個序號讓「每次查詢」都是新的 key，規則只有一條。

## 4. 為什麼只清理自己建立的臨時資源（R3）

原本的真實啟動測試在開始時 `DROP DATABASE IF EXISTS ... WITH (FORCE)`，名稱是固定的。問題：

- 如果剛好有同名的庫（別人建立的、上一次沒清掉但正在被別的程序使用），「先刪」會刪掉不屬於這次的資料，`WITH (FORCE)` 還會踢掉別人的連線。
- 建立第二個庫失敗時，清理程式不知道哪些是「這次真的建立的」。

修改後 `TemporaryDatabases`（測試程式碼）：

1. 名稱：`eip_tmp_<12 碼隨機>_<用途>`，允許的那個以 `_test` 結尾；建立前驗證格式，且不得等於設定中的開發庫／測試庫。
2. `CREATE DATABASE` 成功才記錄；失敗（例如名稱碰撞）不記錄、不刪任何東西。
3. `close()` 只刪記錄過的、反向順序；某一個刪除失敗仍繼續刪其他的，最後把錯誤一起拋出。
4. 先關閉 Spring 應用程式（連線池）再清理；不使用 `FORCE`，暫時被占用（SQLState 55006）就稍等重試。

原則：**清理範圍＝本次確實建立的東西**。「名稱看起來是我的」不夠，必須是「我建立成功的紀錄」。

## 7. 面試重點

**Q1. 樂觀鎖的版本號為什麼不夠，還要比 ID？** 版本只描述「同一筆」的修改次數；換了一筆紀錄，版本可能剛好相同。比對條件必須能唯一識別「我看到的那個東西」：ID＋版本。

**Q2. 表單快照和核准時的過時檢查有什麼不同？** 快照擋的是「打開表單到送出」之間的變動（避免用舊畫面建立申請）；核准時檢查擋的是「申請建立到核准」之間的變動。兩段時間不同，缺一不可。

**Q3. 為什麼「撤銷下班」要送完整精度的上班時間？** 申請的語意是「上班不變」；畫面顯示到秒，資料存到微秒，送截斷值會在核准時改掉上班時間。資料精度要以儲存端為準。

**Q4. React 中「相同條件重新查詢」為什麼沒有發生？** effect 只在依賴值改變時重跑；字串 key 相同就不會跑。解法是讓「每一次查詢」成為新的依賴值（序號），並保留 cleanup 的過期回應丟棄。

**Q5. 測試清理資源的原則？** 只清理自己確實建立成功的資源；不要「先刪同名的再建立」；部分失敗時也只清理已記錄的；清理前先關閉自己的連線。

## 練習（只有這一題）

**背景**：`TodayAttendanceCard` 在員工按下「申請撤銷下班打卡」時，把當下的今日資料存成 `form.seen`，送出時用 `seen.recordId`、`seen.version` 當快照。卡片另外有自動重新查詢（視窗回到前景、切回分頁時）會更新 `data`。

**問題**：假設有人覺得「既然卡片會自動更新，送出時直接用最新的 `data.recordId`、`data.version` 當快照比較準」，於是把送出改成使用 `data` 而不是 `form.seen`。請描述一個具體的時間線（誰在什麼時候做了什麼），說明這個改動會讓員工在不知情的情況下提出一筆內容與他看到的畫面不一致的申請；並說明為什麼後端在這種情況下**無法**發現問題。
