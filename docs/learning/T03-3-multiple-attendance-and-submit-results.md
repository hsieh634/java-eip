## 快速摘要與操作

今日卡片列出所有組、ID、版本、來源與作廢狀態。完成一組後可以再次上班，完成時段合計排除未完成與作廢；不自動扣午休，也不代表專案工時或薪資。

1. 上班 → 下班 → 再上班 → 再下班，前一組會保留。
2. 今日卡片先選「申請目標時段」，再提出撤銷下班或作廢；作廢只影響所選組。有後續組時撤銷較早組會被拒。
3. 「出勤打卡」的更正表單可選指定 ID 或「補登缺少的新時段」。多組未選目標不能提交。每天最多一筆待審更正。
4. 管理端仍逐列更正／作廢，核准時會重新檢查所有有效時段；版本過期或新時段衝突都不會覆蓋資料。
5. 打卡結果不明時兩個新操作停用，按「重送原打卡確認」只送原動作、原 requestId、原定位及下班目標。明確放棄必須先閱讀警告。
6. 切頁／重新整理後只查真實狀態，不自動重送；未確認快照只存目前頁面的記憶體，不跨重新整理保存定位資料。
7. 工時結果不明時原欄位保持鎖定；重試被拒也不清快照，沒有啟用專案仍能確認原提交。確認成功後才能開始新一筆。

## 程式定位與資料流

前端 `src/attendance/useTodayAttendance.ts` 固定操作與提交快照；`src/api/attendance.ts` 檢查成功回應，`TodayAttendanceCard.tsx` 顯示時段、合計與確認操作，`CorrectionForm.tsx` 選目標。工時 `api/timesheets.ts` 與 `timesheet/submitOutcome.ts` 在 API 邊界檢查 EntryResponse；`TimesheetPage.EntryFields.send` 繼續沿用既有 unknown／pending 狀態機。

後端 `AttendanceController` 接收 requestId 與原始定位（下班另有目標 ID＋版本）；Security 先檢查 Session、CSRF、帳號狀態；`AttendanceService` 進交易，`AttendanceWriteRules.lock` 取得組織鎖並重驗身份，再鎖員工列。`AttendanceClockSubmissions` 查持久化原快照；已成功重送直接返回。新操作由 `GeofenceGate` 驗證當下設定，檢查跨列合法性，Repository 條件寫入，`ClockEventLog` 寫原始事件，再保存成功快照。任何失敗一起回滾。

更正流程：畫面指定 ID＋版本 → RequestService 記希望值與歷程（出勤不變）→ AdminService 核准 → 同鎖檢查最新 ID、版本、其他組與時間 → 條件更新 → 歷程。補登是沒有目標的新組，不代表整天沒有出勤。

## 核心設計與實際 SQL

`select id from employee where id = ? for no key update` 與工時的員工列 UPDATE 鎖互斥，卻允許外鍵 KEY SHARE。若用 FOR UPDATE，定位設定交易可能持有設定鎖、等待操作者外鍵，而打卡持有員工鎖、等待設定鎖，形成死鎖。所有出勤寫入順序固定為組織 → 員工 → 定位（新打卡）→ 各業務列。

跨列規則不能只靠版本號：兩個操作可能修改不同 ID，各自版本都正確，合起來卻重疊。`AttendanceWriteRules.validate` 在同交易鎖內排除自己，檢查有效區間；相鄰可接受，未完成必須是最後一組。資料庫部分唯一索引另外保證同員工、同日最多一筆有效未完成；直接 SQL 的完整重疊防護仍依賴服務層，不宣稱索引保證所有重疊。

下班 SQL 明確帶員工、日期、ID、版本、有效與未完成條件；每次修改 version＋1。新增仍使用 ON CONFLICT DO NOTHING，使重複衝突不破壞交易。去重主鍵是 employee_id＋request_id，有效本文的 SHA-256 指紋和動作不符回 409；原成功 DTO 保存為快照。回傳原成功快照不代表目前狀態，前端操作後仍查今日資料。

V8 移除每日有效唯一索引，建立每日有效未完成索引與去重表，不改舊出勤欄位、ID 或外鍵；V1～V7 不改。去重表僅保存定位本文指紋，不保存原始座標；不需要定位的打卡事件沒有座標。

## BUG-TP-001 為何修補在 API 邊界

HTTP 成功與本文可用是兩件事。原本 `api<T>` 的泛型只在編譯時檢查，JSON 解析例外也不是 ApiError，因此 EntryFields 把它當成可修改的失敗。現在新增 API 將本文讀取／解析錯誤轉成中文 UNCONFIRMED_RESULT，並逐欄驗證正整數 ID、版本、專案、原提交日期／內容／分鐘以及時間欄位；只有有效 EntryResponse 才確認成功。既有 DUPLICATE_SUBMISSION 也須含有效 entryId 才能解除追蹤。沒有修改共用 HTTP 或已通過的請假處理。

## 技術問答與一題練習

- 為何前端鎖按鈕還不夠？不同分頁與裝置仍可同時提交，後端鎖與索引才保證不變條件。
- 為何 requestId 要持久化？原上班已完成後收到延遲重送，若只看目前沒有未完成組，就會錯開下一組。
- 為何下班帶 ID＋版本？原請求未成功時目標可能已被更正或換組；舊意圖不能關掉新組。
- 為何重試 403 也不能解鎖？只知道這次被拒，不知道之前的提交有沒有成功。
- 為何不把完成出勤當成工時？出勤與專案投入的領域意義與審核規則不同。

練習：有 09:00～12:00、14:00～18:00 兩組，撤銷第一組下班會違反哪些不變條件？指出服務驗證、交易回滾與畫面提示各負責什麼。
