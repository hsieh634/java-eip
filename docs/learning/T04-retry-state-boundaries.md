## 1. 三分鐘摘要

上一輪讓「結果不明」時表單鎖在原內容，重試只送原內容。這一輪找到兩個邊界：

- **R1-A**：結果不明後的重試，若收到 403（例如 CSRF 失敗）或「專案已停用」，舊程式把它當成「明確拒絕」而解鎖。使用者改成 120 分鐘再送（同一個 requestId）→ 後端說「已建立」（指 90 分鐘那筆）→ 表單被清空，120 分鐘遺失。
  **關鍵**：重試被拒絕，只說明**這一次請求**被拒絕，不能證明**先前那一次**沒有成功。
- **R1-B**：結果不明時，若啟用專案清單變空，送出按鈕因「沒有專案」停用，連「重新送出原內容」都按不到。

**修正**（只改 `TimesheetPage.tsx` 的 `EntryFields`）：
1. 「原提交是否尚未確認」改由 `pending`（未確認快照）是否存在決定，不再由暫時的 `phase` 決定；未確認期間的任何重試失敗都維持鎖定。
2. 確認原提交（有 `pending`）與新增新工時（需要啟用專案）是兩個不同的送出條件。

**證明**：新的 `timesheets-retry-boundaries.mjs` 在基準版本 11 項失敗（24 項中），修正後 25/25；上一輪的 24/24 與既有的 49/49 都仍通過。

## 3. 「本次請求失敗」與「原提交不存在」為何不同

| 回應 | 對「這一次請求」 | 對「先前結果不明的那一次」 |
|---|---|---|
| 201 | 這次建立了 | 先前那次沒有建立（否則會是重複） |
| `DUPLICATE_SUBMISSION` | 這次沒建立 | **先前那次已建立** → 確認 |
| 403（CSRF） | 在進入業務邏輯前就被擋 | **什麼都不知道** |
| 409 專案停用、每日上限 | 這次沒建立 | 依後端檢查順序其實可以推論（重複檢查在前），但前端不依賴這個推論 |
| 網路錯誤、5xx | 不知道 | 不知道 |
| 401 | 登入失效 | 不知道；回登入頁，不以別的帳號重送 |

403 是最典型的例子：它在 Spring Security 的 CSRF 過濾器就被擋下，根本沒有走到「是否已建立」的檢查。所以它只說明「這次請求沒被受理」。上一輪的程式把「首次送出的明確拒絕」與「重試的拒絕」用同一條路徑處理，這就是 R1-A 的根源。

採**保守策略**：未確認期間，除了 201 與 `DUPLICATE_SUBMISSION`，所有結果都不解鎖。代價是極少數情況下使用者需要按「放棄追蹤」（會先看到「原提交可能已經建立」的警告）才能重新編輯；換來的是**絕不**把「已建立 90 分鐘」誤報成「120 分鐘已處理」。

## 4. requestId、提交快照與邏輯操作的生命週期

一次「邏輯上的新增」：

```
建立表單（產生 requestId）
  → 編輯
  → 送出（快照 = 標準化後的內容）
      ├ 201 ………………………………… 結束（換新表單、新 requestId）
      ├ 明確拒絕 ……………………… 回到編輯（同一個 requestId；它底下沒有任何紀錄）
      └ 結果不明 ……………………… 進入「未確認」：pending = 快照（鎖定）
            ├ 重新送出原內容 → 201／DUPLICATE ……… 結束（確認建立）
            ├ 重新送出原內容 → 其他任何失敗 ………… 仍未確認（不解鎖）  ← 本輪
            └ 放棄追蹤（警告後確定） ……………… 結束（換新表單、新 requestId）
```

不變條件：**同一個 requestId 只會搭配同一份內容送出**。上一輪靠 `phase` 守住它；但 `phase` 在重試時會暫時變成 `submitting`，失敗後又被當成「首次送出」處理而落到 editing。改由 `pending` 這個「只在生命週期結束時才清除」的狀態守住，就不會被暫時狀態沖掉。

## 5. 為何新增條件與確認原提交條件必須分開

- **新增**一筆新工時：需要使用者選一個**啟用中**的專案，所以清單為空時送出必須停用。
- **確認原提交**：送的是**已經送出過的同一份內容**，目的是問後端「這個 requestId 建立了沒」。它不需要、也不應該依賴目前的下拉選單（那會改變內容）。專案即使已停用，後端也會先檢查重複——原提交若已建立就回 `DUPLICATE_SUBMISSION`。

所以：`canSubmit = 不是送出中 && (有未確認快照 || 有啟用專案)`。提示文字也分兩種：沒有快照時「請先由管理員建立或啟用專案」；有快照時「不能新增新的工時，但仍可確認上一筆」。

## 7. 面試重點

**Q1. 重試被拒絕，能不能推論原請求失敗？** 不能。拒絕可能發生在處理「是否已執行」之前（例如 CSRF、驗證、權限）。只有能回答「這個冪等鍵是否已執行」的回應（成功或「已存在」）才能確認。

**Q2. 為什麼不用 `phase` 判斷是不是重試？** `phase` 是畫面上的暫時狀態，送出時會被改成 `submitting`；要記住的是「邏輯操作」的狀態，應該用一個只在操作結束時才清除的值（未確認快照）。

**Q3. 為什麼確認原提交不需要啟用專案？** 確認送的是同一份已送出的內容，問的是「建立了沒」；能不能新增新工時是另一個問題。把兩個條件混在一起，就會在最需要確認的時候按不到按鈕。

**Q4. 保守策略的代價是什麼？** 少數情況下使用者必須明確放棄才能重新編輯；但不會出現「以為存了新內容、其實沒有」的誤導。
